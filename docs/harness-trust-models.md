# Harness Trust Standing Configuration

## 1. Per-Harness Trust-Model Findings
- **Claude**: real store is `~/.claude.json` (`projects.<path>.hasTrustDialogAccepted`); `settings.json` is hooks-only and is not consulted for trust. The resolver only ascends from cwd to the enclosing git root, never past it, so a grant on a primary checkout never matches a fresh worktree (whose root is the worktree itself). Exact path only. Seeded non-clobbering (jq merge; preserves other keys and runtime state).
- **Grok**: `~/.grok/trusted_folders.toml`, `[folders."<path>"] trusted = true`. Grok's own docs state a grant covers subdirectories of the same repository but not a nested git checkout, so a worktree is its own, uncovered workspace. Exact path only. Seeded non-clobbering (append-if-absent; preserves runtime appends). Grok also exposes a blanket `[folder_trust] enabled = false` switch (`GROK_FOLDER_TRUST=0`) that would cover arbitrary fresh directories, but flipping it removes per-directory consent entirely rather than adding standing entries for known paths — not adopted here; it needs separate authorization if full worktree coverage is wanted.
- **Pi**: real store is `~/.pi/agent/trust.json`, a flat `"<path>": true` map (verified against the live file on this machine). Its trust-manager walks ancestors up to `/` (not bounded by a git root), so a single grant on `$HOME` covers every path underneath it, including fresh worktrees — the live file already carried exactly this grant before this change. Seeded non-clobbering (jq merge of `"$HOME": true`).
- **Codex**: real store is `~/.codex/config.toml`, `[projects."<path>"] trust_level = "trusted"` (confirmed via `ProjectConfigToml`/`trust_level` strings in the installed 0.153.4 binary). No evidence of ancestor-walk matching, so treated as exact path only, same worktree gap as Claude/Grok. `config.toml` is itself a chezmoi-authoritative render; `[projects.*]` entries are appended after that render rather than living in the template, so a runtime grant Codex records for another path isn't wiped by the next apply.
- **Kimi**: real store is `~/.kimi-code/workspace-trust/wd_<name>_<hash>`, one file per trusted root (`{"root": "<path>", "trustedAt": <ms>}`). The hash in the filename is not reverse-engineered, so pre-seeding a file for a known path risks writing a file Kimi never looks up. Left unseeded.

## 2. Standing Configuration Implemented
- `run_after_seed-harness-trust.sh.tmpl`: runs after every chezmoi apply (not just once), so a store write survives both runtime harness writes and the next apply's template re-render. Each store is updated under its own `flock`, with a post-write read-back check that fails the script if the expected keys did not land:
  - `~/.claude.json` — jq merge of `projects.<path>.hasTrustDialogAccepted = true` for the two known primary paths.
  - `~/.pi/agent/trust.json` — jq merge of `"$HOME": true` (ancestor grant, covers all worktrees for Pi).
  - `~/.grok/trusted_folders.toml` — append `[folders."<path>"]` blocks if absent, for the two known primary paths.
  - `~/.codex/config.toml` — append `[projects."<path>"]` blocks if absent, for the two known primary paths.
  - If `jq` is missing, the script fails loudly (exit 1) instead of silently skipping and being recorded as done.
- Lock paths: Claude and Pi use a dedicated `<store>.chezmoi-seed.lock` file, not the mkdir-based lockfile path the harness itself uses for the same store (reusing it would make the harness's own lock acquisition fail with ENOTDIR against our regular file) — this trades away mutual exclusion with the live harness for not corrupting its locking. Grok and Codex locks are opened non-destructively (`<>`, not `>`) so an existing lock file's content (Grok writes a `pid:timestamp` record into its own) is never truncated before the flock is acquired.
- `umask 077` is set before any store is touched, so temp files and any newly-created store start at `0600` even if a later step fails before the final `chmod`.
- This doc is chezmoi-ignored as a directory (`.chezmoiignore`: `docs`), so it and its parent directory are not installed to `~`.

## 3. Verification Performed
- The only artifact produced by prior verification attempts is `data/.../verification-grok.log`. Its content is `grok --help` usage text followed by `exit: 0` — the binary printed its help and exited without starting a session, so it does not demonstrate that any trust dialog was or was not shown. No verification artifacts exist for Claude, Pi, Codex, or Kimi.
- This round's fix was verified by: `bash -n` syntax-checking the modified script, and a dry run of the full script against a throwaway `$HOME` (fresh run, idempotent re-run with simulated pre-existing runtime state in each store, and a `jq`-missing failure path) to confirm the merges, the Grok/Codex appends, the read-back checks, and the lock-path change all behave as intended. No interactive harness session was launched, so no trust dialog was observed directly.

## 4. Explicit Limitation Statement
- Kimi is unseeded entirely (hash-keyed store, algorithm unverified).
- Claude, Grok, and Codex only cover the two known primary paths; fresh per-spawn worktrees under `~/.treehouse/<host>/<n>/<repo>` are not covered on any of them, because each resolves trust by exact path (or, for Claude, by an ancestor walk bounded at the git root) and a worktree's path isn't known ahead of time. Grok's `folder_trust` disable would cover this for Grok but removes per-directory consent entirely; adopting it is a bigger step than the intent's "standing configuration in the harnesses' own config surfaces" ask and needs separate authorization.
- Pi is the one harness where this is actually closed: its ancestor-walk plus the `$HOME` grant above means any path under `$HOME`, including every fresh worktree, is already trusted — no blanket "trust everything, no prompts" bypass needed.

See `run_after_seed-harness-trust.sh.tmpl`, `private_dot_codex/config.toml.tmpl`, and git history for details.
